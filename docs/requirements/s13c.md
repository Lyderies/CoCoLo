# S13C: test headroom after IP-A

Base: 0.8.67 (`ce81bd96`), branch `fix/s13c-headroom`. Owner rule: least test running; a recurring overrun is fixed at its
cause, never by a bigger budget, a weaker assertion or a removed test. Test-only: no product code changed, so no runtime
digest re-record and no version bump.

The 0.8.67 full run (`--jobs 16`, about 498 units) had `codex:tests.test_project_driver` at 523.8 s against a 520.4 s
budget-debt ceiling, `codex:tests.test_project_start` at 175.8 s against 183.4 s (and E2c-1 failed once under load: "the due
projects were not serving within one interval"), `codex:tests.test_host_slots` at 68 s (51 s on 0.8.66) and
`codex:tests.test_lost_run_settlement` at 121 s. S1 (E1b sole ledger owner), S2 (preparation cleanup start-up reads) and S3
(U1 rollover) all landed in 0.8.67.

## Requirements

- **S13C-1:** `codex:tests.test_project_driver`, `codex:tests.test_project_start`, `codex:tests.test_host_slots` and
  `codex:tests.test_lost_run_settlement` each total at most 80% of their budget-debt ceiling (or layer budget), measured as
  the sum of the module's fragments' seconds, with full-run parallelism (`--jobs 16` beside `root:test_install` and
  `root:test_setup_wizard_direct`).
- **S13C-2:** the start-up test `test_E2c_1_a_stopped_project_with_due_holds_starts_without_any_client` is deterministic
  under load without losing what it proves (E2c-1, "serving within one interval"): the starter's own interval bounds when
  each start begins, the starter's own path from `begin` to the host process being spawned is bounded (`SPAWN_BOUND`, 1.0 s,
  so a delay inside the starter fails it), and each host serves within the start's deadline
  (`project_host_client.START_TIMEOUT_SECONDS`) of its own spawn. The bound from `begin` to serving cannot be held at about
  1.2 s under load without a product change (the host compiles the runtime in its own process): see `s13c/STATUS.md`.
- **S13C-3:** no assertion is removed or weakened. Every changed assertion, renamed test or changed fixture behaviour is
  paired old -> new in [`s13c/assertions.md`](s13c/assertions.md).

## Findings (profile first)

1. **0.8.67 is not slower than 0.8.66 in these four modules.** The same four modules, `--jobs 16`, alone, on `afb6f610`
   (0.8.66) and `ce81bd96` (0.8.67): driver 501 / 545 s, start 180 / 202 s, host_slots 61 / 56 s, lost_run_settlement
   131 / 114 s. The 0.8.67 first run (832 / 310 / 101 / 232 s) was taken at machine load 15 to 26 from other work; module
   seconds are sums of fragments, so they grow with load by up to 1.5 times. The reported 51 -> 68 s of host_slots is
   inside that spread; no S1-S3 step added a measurable cost per test.
2. **The modules are CPU-bound by their fixed per-test path.** One `ProjectDriverTests` pass (24 tests) uses 22.7 s of
   in-process CPU and 13.9 s of child-process CPU for 43 s of wall (85% of one core). Per test: a real collector, account
   services and project host (threads), about ten in-process CLI calls over sockets, `git`, `sandbox-exec`, the fake
   clients and one separate `dispatch` interpreter. Under `--jobs 16` that CPU is oversubscribed, which is what the budget
   check measures.
3. **Waits on the one-second sweep.** `test_lost_run_settlement` and `HostRestartTests` wait for a successor host's sweep
   (`SWEEP_SECONDS` 1.0). TESTSPEED3 fixed this for the settlement modules only.
4. **No bytecode cache for the test-only interpreters.** `separate_dispatch` (`-I -B -S`), the crash-host fixture
   (`-B`), the collector launcher, the `cli.py` runs and the killer in `test_project_start` (`-I -B`) compile the runtime on
   every start (0.3 s quiet, more under load).
5. **`getconf` per `temp_roots()` call.** `host_paths.darwin_directory` starts a `getconf` process on every call; one
   driver test calls it 26 times (about 0.1 s quiet, more under load).
6. **Fixed observation windows.** Three crash tests of `test_lost_run_settlement` watch "several sweeps" with `sleep(5)` and
   a 6 s loop, which at a 0.1 s sweep would be 50 and 60 sweeps; the product wait is in sweeps, not seconds.
7. **Idle windows slept through.** Three `HostReplacementTests` sit through the host's 4 s idle window plus the loop's
   one-second check (about 5 s each, a third of `test_host_slots`); the module already moves a host's clock instead in the
   PREPCLEAN tests.
8. **E2c-1's serving bound.** The test allowed one interval plus one fixed second (about 1.4 s with the test's 0.2 s
   interval) from the collector being ready for two real project-host processes to start (each compiles the runtime with
   `-B -X pycache_prefix=/dev/null`) and to answer. Measured from `begin`: the starter reaches the spawn in 0.06 s quiet and
   0.1 to 0.3 s loaded; the host then serves 0.6 s after `begin` quiet and 0.75 to 1.3 s loaded. Passes alone, fails when
   other work holds the CPUs; the host's share is product start-up cost that no test cache reaches.

## Fix

- `DriverHarness` (`test_project_driver`, inherited by `test_lost_run_settlement`, `test_host_slots`, the settlement modules):
  `sweep_seconds = 0.1` patches `project_driver.SWEEP_SECONDS` for the test and restores it after (a class that needs the
  product value sets `None`); `setUpClass` gives the class one bytecode cache (`dispatch_pycache`) for its separate
  dispatches and the crash-host process; `darwin_directory` is memoised for the class.
- `test_lost_run_settlement`: the crash host runs with the class cache; the two "several sweeps" windows wait for a counted
  number of completed sweeps (`count_sweeps` / `through_sweeps`: `_settle_lost` calls that returned without raising) instead of 5 s and 6 s.
- `test_project_start` (`StarterBase`): the collector launcher, `cli.py` runs and the killer share a per-class cache; E2c-1
  splits the serving bound at the spawn (starter path from `begin` bounded by `SPAWN_BOUND`, host from its spawn within the start deadline) and compiles the runtime into the class cache in `setUpClass`.
- `test_host_slots`: the idle-replacement tests move the host's clock past its idle boundary (`until_idle`).
- `test_account_settlement_driver`: the TESTSPEED3 per-class cache and 0.1 s sweep move into `DriverHarness` (same values).
