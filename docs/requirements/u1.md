# U1 — automatic orchestration lifetime (Unit 3.9, slice 5)

Base: `afb6f610` (0.8.66). Authority: decision 310, RT-18/RT-18j,
TERM-4 and TERM-38; remaining-analysis slice 5 and p37–39 audit section 181.
VERSION and the runtime digest catalogue belong to the primary at merge.

## Sizing (O0C-U1-1)

The token analysis measured a fresh context of about 45k, mean growth 1.2k
per response (median 0.8k), 177 responses in 2.5 hours, and 155 tool results.
A 200k soft window leaves 155k: about 129 mean-growth responses; the 250k
hard window leaves 205k: about 171 (256 at median growth). At one run per
response, reaching 512 would take 614.4k growth plus 45k = 659.4k context;
4,096 events would take 4,915.2k plus 45k = 4,960.2k. Those are estimates,
not safety bounds: 512 runs fit the hard-window growth budget at 400.4 tokens
per run; 4,096 events fit at 50.05 tokens per event. Batches, short calls,
replay and service-side events have no required minimum token cost. Thus a
single <=250k session CAN reach either cap; context rollover alone is
insufficient. 512 registration attempt rows, report MAX_RUNS (open attempt
rows, registration attempt rows, and distinct mixed runs), and 4,096 journal
events are independent boundaries. The open event counts; one event is
reserved for close. Replay charges no new event or run.

## Accepted requirements

- **O0C-U1-2:** At a safe session hand-off, one authenticated product call
  atomically closes the current orchestration and opens its successor. It uses
  the ordinary close checks and reserved event, keeps the complete old report
  readable, and links both ends to one versioned, sealed hand-off record.
  A transaction interrupted anywhere rolls back both ends; replay after a lost
  reply returns the same successor without consulting the clock. Changed
  parameters under the same identity conflict. There is exactly one open
  orchestration in this chain, including when the project open limit is one.
- **O0C-U1-3:** Before each new run or journal mutation the runner calls the
  same product continuation path with cause `capacity`. The product checks
  registration rows, open report rows, mixed distinct report runs, and event
  headroom independently. At a boundary it rolls over automatically within
  the provider session. Safe work continues on the returned handle. No owner
  action or user-facing capacity refusal is part of this path. Unfinished
  work retains the old orchestration and returns only an internal waiting
  status; the runner drains it and retries before admitting more work.
  Replayed continuation checks cannot create another successor.
- **O0C-U1-4:** Checkpoints may persist bounded structured resume state as work
  progresses; later checkpoints carry it forward. `orchestration.packet`
  generates the packet from sealed project records, including after restart
  without a hand-off file. The successor inherits this state and the hand-off
  link. Provider session IDs are metadata on that link; authenticated project
  supervisor scope remains unchanged. The runner alone starts/stops provider
  processes; this unit adds no process launcher. Resume state is at most
  2,048 canonical UTF-8 JSON bytes (new per-checkpoint bound, not a lifetime
  count), with a past-bound test. Existing 8,192-byte checkpoint and 16,384-byte
  wire bounds remain in force.
- **O0C-U1-5:** Test small independent boundaries and repeated rollover beyond
  each, exact replay at the last ordinary event and at reserved close, mixed
  report rows (including overlapping registrations/opens), rollback between
  close/open and after both writes, lost replies and reopen, revocation,
  malformed calls and resume-state size overflow. Include a cheap real
  512-registration boundary and one-past continuation. Preserve existing
  low-level refusal tests: those guards protect direct callers; the runner's
  automatic continuation path checks before reaching them.

## Runner/core integration contract

Runner v1 is external and read-only in this unit. It cannot be invoked by
this product library. Its adapter must call the enrolled product entry point
`client_runtime.orchestration_lifetime_client(state_root, project_root,
host_client=..., orchestration_handle=..., expected_sequence=...,
request_id=..., session_id=..., next_session_id=..., cause=...)`.
`cause='session'` is unconditional at RT-18's 200k phase boundary / 250k safe
point; `cause='capacity'` is required before every new registration and journal
mutation and uses the same session ID for both ends. This makes exactly one
`orchestration.rollover` exchange through the existing project history
endpoint. The caller persists the identity and exact inputs before sending,
reuses them after interruption, drains work on an internal waiting note, then
switches to the returned snapshot handle/sequence. The runner must serialize
continuation with admission/mutations for its orchestration. Session process
replacement follows a committed hand-off only; a lost reply is reconciled
before starting the next provider session. It never asks the owner to do this.

Persist state with `orchestration.checkpoint`'s optional `resume_state` object;
read with `orchestration.packet` and the current handle. The packet includes
state, current snapshot, and the hand-off record (or null initially). The
hand-off names old/new handles, old/new provider session IDs, cause and request
digest. The old orchestration report remains the existing product report,
with all checkpoints counted and up to its existing 64 recent checkpoints
shown. It is subject to the existing 90-day closed-history retention. This
unit does not claim to have modified or live-tested the external runner, nor
to implement the whole terminal hand-off browser/retention policy.

In runner v1, the session call belongs in `Runner.do_handoff` after its second
`safe_point` check and record synchronization, before `end_session`. Persist
its continuation identity and planned next provider session ID before the
exchange; `start_next` must reconcile that identity and read the product packet
before `begin_session`. The provider session ID can be a runner-generated
stable generation ID chosen before the provider starts. Capacity continuation
belongs before the runner admits each new run/checkpoint, retaining that ID.
The existing model/provider/effort tuple is not a unique session ID. This is an
integration contract for the read-only runner, not a claim that it already
calls these new product operations.
