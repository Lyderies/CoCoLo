# M11 — dispatch admission at slot exhaustion

Authority: O0c remaining-work analysis, M11 row and independent build slice 3.
The starting requirement catalogue and `tests/requirements` contain no M11 entry.
Keep the existing `DispatchSlotRegisterTests` requirement and assertions unchanged:
“a host with no dispatch slot left refuses a new run at registration, before any claim,
so the run is never admitted only to meet dispatch_full; the host is replaced
(exhausted) and the next run registers on a fresh one.”

### M11-1 — Refuse before registration or claim

Configure two dispatch slots before starting the project host. Occupy both through
normal CLI dispatches, keep the host busy, and open a third run through
`learning-open-host-run`. Its host registration returns the retryable
`history_service_unavailable` refusal; it creates no driver registration, persisted
project registration, or account claim. An account open receipt may already exist;
the CLI must report `project_host_registered: false`. Existing registration replay
remains idempotent at exhaustion.

### M11-2 — Serve existing work until drain

An exhausted host stays alive while existing runs are busy, including a live
child. Status, result recording, and normal cancellation still work. Recording
one run does not interrupt the other child; cancelling and recording that child
then drains the host. Neither admission refusal nor a status call forces a
replacement while work is busy.

### M11-3 — Replace automatically and dispatch the retry

After both runs drain, the production service loop stops the exhausted host
without a test calling close or constructing a replacement driver. The next normal
CLI open starts its replacement through the normal ensure-host path. Retrying the
same third open keeps its account run identity, registers on the fresh host, and
dispatches successfully. Replacement is driven by exhaustion, without waiting for
the ordinary idle timeout.

Retry identity follows `open_inputs_digest`: a refreshed advisory route
availability audit must not conflict with the refused attempt's account open.
If the account receipt and pending binding are retained, retry replays that
receipt, handle and original observation deadline without another binding hold,
admission, registration, claim or capacity reservation. Current native authority
and all original execution inputs remain checked; changed original inputs still
conflict. This is the idempotent-open recovery permitted for M11.

### M11-4 — Bind the lifetime limit to its recovery evidence

The lifetime-cap registry entry for `project_driver.py::_register` names the
two-slot CLI scenario and describes refusal, busy drain, and replacement as the
end of the dispatch slot lifetime. Preserve the existing synthetic M11 test.
