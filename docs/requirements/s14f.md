# S14f + S9-WAIT: owner-thread maintenance bounded in work and in waiting (decision 388)

Authority: PLAN-0.4.0-v2.md S14f; reviews/040-s16-e4/RESULT-codex.md (MED A, LOW A); RS-10 / S7 owner request bounds.

## Design and safety argument
Requirement: the paged answer is never smaller than the whole-scan answer at any point it is used to prune. Skipping or
delaying a prune is always safe (it only delays retention); nothing here deletes more than the whole computation.

- Edge keys only: a custody digest that is no `runtime_lineage` predecessor protects nothing, so only edge keys are kept.
- One cycle = read edges (key pages) -> history rows (rowid windows of `active_run_capacity`, then `launch_inputs`) -> walk the
  protected paths (one visited set: a walk stops at an edge an earlier walk kept, whose rest that walk kept too; linear) ->
  delete the unprotected edges in pages. Every pass spends at most `CUSTODY_PASS_ROWS` units over all of these (S14F-5).
- Clock (S14F-4). Custody is monotone in the cutoff: a row in custody at cutoff c is in custody at every c' <= c. The cycle uses
  ONE cutoff C = start - retention, fixed at its first pass. A pass at time t >= start (forward or no movement): the whole answer
  at t uses c_t >= C, so it is a subset of what C keeps; judging later rows at C keeps more, never less. A pass at t < start
  (rollback): C would keep less than the whole answer at t, so the cycle restarts with t as its new start. A fixed cutoff alone
  is unsafe for rollback and a per-pass cutoff is unsafe for rollback too (r1 reproduction), so both are needed: the earliest
  cutoff for the cycle, and a restart when the clock goes below it. Pruning passes are gated the same way.
- Rows changing during a cycle (S14F-6). Under a fixed C, only changes that ADD custody for an edge key can make the cycle short:
  an insert or update of an `active_run_capacity`/`launch_inputs` row naming an edge key (a delete+reinsert is an insert, whatever
  rowid it gets), a binding insert or an expiry extension, a live `run_slot`/`binding` hold for such an input, or any lineage
  insert/update. TEMP triggers (per connection; never in the stored schema, a backup, or `total_changes` at rest) count exactly
  these. Deletes, release transitions and expiry reductions only remove custody and are deliberately not counted, so ordinary
  retention purges do not stall the cycle. A commit by another connection (`PRAGMA data_version`), a schema change or VACUUM
  (`main.schema_version`; VACUUM may renumber rowids under the cursor) or a different connection restarts the cycle; ledger
  maintenance also resets the scan explicitly after VACUUM. This replaces the max-rowid comparison, which a delete+reinsert of
  the top row evaded.
- The scan state is in memory on the store; a restart begins a new cycle. Open and the 17->18 upgrade keep the whole computation.
