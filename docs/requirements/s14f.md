# S14f + S9-WAIT: owner-thread maintenance bounded in work and in waiting (decision 388)

Authority: PLAN-0.4.0-v2.md S14f; reviews/040-s16-e4/RESULT-codex.md (MED A, LOW A); RS-10 / S7 owner request bounds.

| Requirement | Acceptance |
| --- | --- |
| S14F-1 | `sweep_account_retention` computes custody in passes of at most `CUSTODY_PASS_ROWS` (256) history rows (rowid windows of `active_run_capacity`, then `launch_inputs`), keeps only digests that are lineage edge keys, and prunes only when a cycle has seen every row. The answer equals the whole-history custody restricted to edge keys; no live run is missed at any position/bound. |
| S14F-2 | A pass on a 60k-run history stays inside LEDGER_REQUEST_WAIT_MS/8. |
| S14F-3 | The sweep uses the paged scan; open and the 17->18 upgrade keep the whole computation (S14E-1/2 pin its query plan). |
| S9-WAIT | `_begin_exclusive_maintenance` waits at most `MAINTENANCE_READER_WAIT_S` (5 s) for health-copy readers; a stalled reader gives a plain `LedgerError`, store unchanged, and a later attempt succeeds. |

## Design and safety argument
Custody under-count is a safety bug, so the paging is exact, not sampled. A custody digest that is not a `runtime_lineage` predecessor protects nothing in `prune_lineage`, so only edge keys are tracked. A cycle is discarded (never used to prune) when the edge set changes or a source table's highest rowid falls (rowid reuse). A runtime that has a lineage edge has been taken over and cannot create new runs, so rows cannot appear behind the cursor for a digest that matters; each pass uses its own clock and an earlier pass saw an earlier cutoff, which only keeps more custody. Skipping or delaying a prune is always safe (it only delays retention); nothing here deletes more than before. The scan state is in memory on the store; a restart begins a new cycle.
